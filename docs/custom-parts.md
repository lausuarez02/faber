# Agent-made parts (create_part)

When `search_parts` finds nothing that fits (a soil sensor, a relay board, a pump, a GPS module),
an agent can make the part itself with `create_part`. The part is **data, not code**: pins,
physical facts and one behaviour template with numbers. Fabwright builds the simulation model from
the template, so nothing an agent writes is ever executed, in the CLI, the server or a person's
browser. Decision record: [decisions/0003](decisions/0003-round5-see-it-work.md) (agentparts, C4).

Every such part is labelled **`agent-made: behavioral, unverified`** in `search_parts`,
`fidelity_report`, the exported BOM and WIRING, and on the part's drawing (a dashed AGENT-MADE
tag). It behaves the way the agent described it. Passing tests show the firmware agrees with that
description, not that the real module behaves the same: check the pinout and supply voltage
against the seller's page before wiring the real thing.

## Where it lives

```
my-device/
  fabwright.json
  parts/
    soil-moisture-sensor/
      part.json      # format "fabwright-part/1", written by create_part / update_part
      visual.svg     # only when the agent gave a drawing (sanitized)
```

The files are written only through the tools, so each change is an undoable step in the history
and the action log. The project's registry is the built-in catalog plus these parts, reloaded
when `parts/` changes (another process, `undo`); a changed part restarts the simulation at 0 ms.
Ids must not be built-in types: `create_part` refuses and names the built-in. If a later Fabwright
ships a built-in with the same id, the project keeps using its own part and says so in
`list_project_parts`.

JSON Schema: [`packages/parts/custom-part.schema.json`](../packages/parts/custom-part.schema.json)
(generated by `pnpm gen` from `packages/parts/src/custom/schema.ts`).

## The tools

| Tool | CLI | What it does |
| --- | --- | --- |
| `create_part {part, svg?, why?}` | `fabwright create-part part.json [--svg visual.svg]` | Validate, compile and save a new part; returns its pins, state fields and warnings |
| `update_part {id, part?, svg?, why?}` | `fabwright update-part <id> [part.json] [--svg F \| --no-svg]` | Replace the definition and / or the drawing (`svg: null` = generated drawing). Refuses to drop pins that wires use |
| `list_project_parts {}` | `fabwright project-parts` | The project's agent-made parts and any file that failed to load |

`GET /api/project-parts` on `fabwright serve` gives the parts with their SVG to the web canvas, which
compiles them again in the browser (and sanitizes the SVG again).

## Common fields

| Field | Notes |
| --- | --- |
| `id` | kebab-case, not a built-in type |
| `name`, `category`, `description` | `category` is any part category except `board` |
| `pins[]` | `{id, type: digital\|analog\|power\|ground\|passive, label?, voltage?: {min, max}, protocols?, description?}`; `x`/`y` only with your own SVG |
| `power` | optional `{vcc, gnd, min_v, max_v}`; default: the first power and ground pin, the power pin's voltage range |
| `current_ma`, `price_usd`, `dimensions_mm`, `mass_g`, `buy_links`, `datasheet` | physical data (C2) for `plan_device` and the BOM; warned when missing |
| `usage` | `{wiring, example?, libraries?}`: what `get_part` shows the next agent |
| `props` | extra props; each behaviour adds its own (the field you set with `set_sensor_value`) |

Every behaviour publishes state you can test with `expect_part` (listed in the `create_part`
result as `state`) and a `label` drawn on the part. A part with a power pin is off (and says how to
power it) until that pin sees at least `min_v`, and reports over-voltage above `max_v`.

## Behaviour templates

### digital-input: PIR, IR obstacle, tilt, hall switch

```json
{ "kind": "digital-input", "output": "OUT", "field": "motion", "active_level": "high", "drive": "push-pull" }
```

The output pin is driven at the supply voltage (or pulled low only, for `open-drain`) from a
boolean field. Set it with `set_sensor_value pir.motion true`, a scenario `set` step, or
`press` / `release`. State: `motion`, `level`, `powered`.

### analog-sensor: soil moisture, gas, flex, force

```json
{ "kind": "analog-sensor", "output": "AOUT",
  "quantity": { "id": "moisture", "unit": "%", "min": 0, "max": 100, "default": 40 },
  "curve": [{ "value": 0, "volts": 3.0 }, { "value": 100, "volts": 1.2 }],
  "digital": { "output": "DO", "threshold": 60, "when": "below", "active_level": "low" } }
```

The output is a voltage source with `output_ohms` (default 1 kΩ) at the curve's voltage,
piecewise linear between points. With `ratiometric` (default) the volts are at a 5 V supply and
scale with VCC. `digital` adds a comparator pin. State: `moisture`, `volts`, `powered`,
`triggered`.

### actuator: pump, motor, solenoid, relay board

A load between two terminals:

```json
{ "kind": "actuator", "drive": "load", "plus": "+", "minus": "-", "rated_v": 5, "rated_ma": 180,
  "effect": { "id": "flow_ml_min", "unit": "ml/min", "at_full": 1200 } }
```

It is a resistor of `rated_v / rated_ma` in the circuit, so a PWM-driven transistor or driver sets
its level (PWM is averaged). Wired straight to a GPIO it draws far more than the pin can give and
the simulation reports `gpio-overcurrent` with the fix (a transistor, MOSFET, relay or driver).
State: `on`, `level`, `volts`, `current_ma`, `direction`, plus the `effect` field and `force_n`
(reported only, not applied to the robot world).

A logic-controlled module:

```json
{ "kind": "actuator", "drive": "logic", "input": "IN", "active_level": "low", "input_ohms": 1000,
  "contacts": { "com": "COM", "no": "NO", "nc": "NC" } }
```

The input loads the GPIO (`input_ohms`, to VCC for active-low optocoupler inputs). Relay contacts
are real switches in the circuit, so `COM → 5V`, `NO → pump.+` runs the pump. State: `on`,
`level`, `powered`.

### i2c-device: a sensor or chip read with Wire

```json
{ "kind": "i2c-device", "address": 64, "pullup_ohms": 10000,
  "who_am_i": { "reg": 15, "value": 167 },
  "registers": [
    { "reg": 0, "bytes": 2, "field": { "id": "temperature", "unit": "°C", "min": -40, "max": 125, "default": 22.5, "scale": 100, "signed": true } },
    { "reg": 16, "name": "config", "writable": true, "value": 0 } ] }
```

Needs one pin with `protocols: ["i2c-sda"]`, one with `["i2c-scl"]` and a power pin. The firmware
writes a register address, then reads or writes bytes from it (the pointer auto-increments).
A `field` register holds `round(value × scale + offset)` (two's complement when `signed`, big
endian unless `endian: "little"`); `set_sensor_value tmp.temperature -5.25` changes it while the
sketch runs. Writes to registers not marked `writable` are acknowledged and ignored, with an info
diagnostic. Several `address` values add an `address` prop. Faults (`inject_fault i2c_nack` …)
work as on built-in I2C parts. State: `address`, `reads`, `writes`, each field, each named
register's raw value.

### uart-device: a serial module (SoftwareSerial pins)

```json
{ "kind": "uart-device", "rx": "RX", "tx": "TX", "baud": 9600,
  "responses": [{ "match": "AT", "reply": "OK" }, { "match": "READ", "mode": "prefix", "reply": "T={temp}" }],
  "unknown_reply": "ERROR", "greeting": "READY",
  "stream": { "every_ms": 1000, "text": "$GPGGA,{lat},N,{lon},E" },
  "fields": [{ "id": "temp", "min": -40, "max": 85, "default": 21, "decimals": 1 }] }
```

Bit-level 8N1 on the part's pins, like the ESP-01 model: wire `TX` to the board pin
`SoftwareSerial` receives on and `RX` to the one it sends on. Lines end at CR or LF; the first
matching response is sent after `delay_ms` (default 1 ms). The board's hardware Serial pins
(D0/D1) are the serial monitor and do not reach parts. State: `lines_received`, `replies_sent`,
`unmatched`, `last_line`, `last_reply`, `framing_errors` (wrong baud) and the fields.

### display: a screen on an existing controller

```json
{ "kind": "display", "controller": "st7735", "resolution": { "w": 240, "h": 240 },
  "ram": { "w": 240, "h": 320 }, "offset": { "x": 0, "y": 80 }, "ips": true, "round": true }
```

Reuses the built-in `ssd1306` (`ssd1306-oled-i2c`), `st7735` or `ili9341` model, so the same
libraries work (Adafruit_SSD1306, U8g2, Adafruit_ST7735 / ST7789, Adafruit_ILI9341). Leave
`pins` out to get the controller module's pins; if you list pins, keep its pin ids. `resolution`
(st7735 / ili9341) changes the panel size; `ram` + `offset` model a glass that shows a window of
a bigger controller RAM (the ST7789 240x240 above, driven by `Adafruit_ST7789 tft.init(240, 240)`);
`ips` is for IPS glass, whose library turns inversion on to get normal colours; `round` draws a
round bezel. `gc9a01` reuses the built-in `gc9a01-round-tft` (240x240, round). The window is fixed,
so libraries that move it with rotation (rotations 2-3 on some panels) show a shifted picture.
The e2e test `apps/web/e2e/agentparts.spec.ts` runs exactly this part with an Adafruit_ST7789
sketch in the browser.

## Drawings

Without `svg`, Fabwright draws a labelled module: the name, one header row with the pin labels, a
status light or value readout bound to the state, and the AGENT-MADE tag. Displays get a glass
area where the live pixels appear.

With `svg`, give `size: {w, h}` (the viewBox) and `x`/`y` for every pin. The SVG is rebuilt from
an allowlist: `<script>`, `<foreignObject>`, `<style>`, animation elements, `on*=` handlers,
links other than `#id`, `url(…)` other than `url(#id)`, `javascript:` and images other than inline
PNG / JPEG / GIF / WebP are removed (each removal is a warning in the result); DOCTYPE and entity
declarations are refused. Ids are prefixed with the part id. `data-bind="attr:stateKey"`
attributes work as on built-in parts, e.g. `data-bind="opacity:ledOpacity"`. A display's SVG
needs a `<rect data-screen="WxH">` where the pixels go.

## What it cannot do

- No code: a part cannot compute anything the templates do not offer (filters, protocols beyond a
  line-based UART script, SPI devices other than the display controllers, 16-bit I2C register
  addresses).
- Real-world effects are not modelled: noise, drift, response times, inrush and stall currents,
  inductive kick-back, mechanical delays.
- Actuator forces do not move the robot world (`world.robot` needs the built-in `dc-motor`).
